> 来历：2026-11-02 分组系统重构第 23 轮，一次批量删除把 6 本书的 DB 行误删
> （根因见 `docs/架构-分组系统-00-真源.md` §11.5）。本文是**当场把它 100% 还原出来**的流程，
> 以后遇到"数据被误删/需要证明删了什么"直接照做。

## 0. 先说两条最关键的结论

1. **只拷主库文件（不带 `-wal`）= 拿到"最后一次 checkpoint 之前"的旧状态。**
   本工程当时用这一招把被删的 6 行**整行**捞了出来（书名/路径/分组/进度/文件大小全在）。
   带 `-wal` 打开看到的才是**当前（已删）**状态。
2. **打开副本时 SQLite 会自己 checkpoint 并可能把 `-wal` 清掉。**
   ⇒ 第一件事永远是**把 `novel.db` / `-wal` / `-shm` 三个文件原样复制到"只读存档"目录，之后所有实验都在新副本上做**。
   （本流程第一次就踩了：直接在工作副本上 `sqlite3 connect` 之后 `-wal` 被合并，白做一轮。）

## 3. 用两份副本对比（核心手法）

```powershell
# 存档（只读，永远不动）
Copy-Item dbforensics\novel.db* dbforensics\pristine\ -Force
# 实验副本 A：只放 novel.db（= checkpoint 前旧状态）
mkdir view_precheckpoint ; Copy-Item pristine\novel.db view_precheckpoint\
# 实验副本 B：db + wal + shm（= 当前状态）
mkdir view_withwal       ; Copy-Item pristine\novel.db,pristine\novel.db-wal,pristine\novel.db-shm view_withwal\
```

查询（本机 python 3.12 自带 `sqlite3`，无需装任何东西）：

```python
import sqlite3
con = sqlite3.connect(r"...\view_precheckpoint\novel.db")
cur = con.cursor()
print([r[0] for r in cur.execute("SELECT name FROM sqlite_master WHERE type='table'")])
for r in cur.execute("SELECT id, bookGroup, bookName FROM books ORDER BY id"):
    print(r)
```
本次实测对比：`view_precheckpoint` 里 `books` 有 id **32..37** 的 6 行；`view_withwal` 里没有
（同时 `book_groups` 从 20 行变 28 行：新加了 A1..A6）⇒ 差异就是"这期间发生的写操作"。

## 4. 把"丢的行"完整打出来（可直接用于复原）

按主键差集定位，再把整行 dump 成 JSON 存档：
```python
cols = [d[1] for d in cur.execute("PRAGMA table_info('books')")]
rows = list(cur.execute("SELECT " + ",".join(cols) + " FROM books WHERE id IN (32,33,34,35,36,37)"))
import json; open("deleted-books-6.json","w",encoding="utf-8").write(json.dumps([dict(zip(cols,r)) for r in rows], ensure_ascii=False, indent=1))
```
**判断"损失有多大"就看这几列**：`durChapterIndex` / `durChapterPos` / `durChapterTime` /
`latestChapterTitle` / `totalChapterNum`——全 0 且标题 None ⇒ 这本书**从没被读过**，重导即无损复原。

> 同一个"误删"如果发生在**被删后还重启过应用**的场景，§3 的 checkpoint 旧状态可能已被覆盖，
> 那时只能退到下面这条（本轮**未真跑通**，标【待验证】）：

## 5. 【待验证】WAL 帧回滚（按帧截断拿"某个历史时刻"）

WAL 是"页面版本日志"，理论上按帧边界截断 + 删 `-shm` 就能让 SQLite 看到"截断点那一刻"的状态：
```
WAL 头 32 字节（magic=0x377f0682/0x377f0683、pageSize 在偏移 8）
每帧 = 24 字节帧头 + pageSize
→ 逐个 k 复制 novel.db + WAL 前 32+k*frame 字节（不要 -shm），打开后查目标表
```
本轮因§0 第 2 条（副本的 `-wal` 已被 checkpoint 掉）没跑完，**结论待验证**；真要恢复时把
存档的 pristine `-wal` 重新展开再试，别在已经被 checkpoint 的副本上试。

## 6. 复原手段（本工程场景）

- 源文件还在设备沙箱 `<filesDir>/*.txt` ⇒ 导出 → 用户在 App「书籍导入（本地导入）」重新选一次。
  `books.isLocalBook=1`、`bookUrl` 指向沙箱；重导后 `id`/`sort` 会变，其余等价。
- **不要**为了"凑数量"批量重导全部源文件（会重复建行）。
- 进度/书签无需抢救的前提是 §4 那几列全 0；若有进度，`BookRename.purge(name)`
  （`common/utils/BookRename.ets:261-290`）在删行时已把 `bookmarks` / `book_history` /
  `readRecord` / 各类 Preferences 键一起清了 ⇒ **有进度的书基本救不回来，只能靠备份**。
