## 二、已完成：自绘两档「文字偏左」修复（`dcc1cc8`）

### 根因（架构层，已确认）

自绘两档是**双引擎 + 硬切行**：

```
断行：@ohos.graphics.text（para.layoutSync → getLineMetrics）→ 每行字符区间
渲染：ArkUI Text（每行一个 Text，行内容固定）
```

- 两者对「单字推进宽度」的度量不完全一致；
- 显式 `letterSpacing` 把字距钉死 ⇒ `TextAlign.JUSTIFY` **拉不开**；
- 一行排不满时，余量（不足一个整字）**整块堆在右边** ⇒ 大字号下右侧留白接近一个整字，看着像"文字偏左"。
- 实测（手机 26fp）：12 字 × 89px = 1068，可用宽 1140 ⇒ 行尾空 **72px**。

### 修法（方案 B · 闭环）

```ts
// ReaderScrollView.rowLetterSpacing(row) / ReaderPageNoAnim.lineLetterSpacing(line)
measuredPx = MeasureUtils.measureText({ textContent, fontSize, fontFamily,
                                        fontWeight: scrollFontWeight(...), letterSpacing: LETTER_SPACING_FP })
deltaPx = 可用宽 - measuredPx - 2        // 2px 安全余量（防折行）
addPx   = min(deltaPx, fontSizePx * 1.2) / 有效字数   // 有效字数 = text.length - prefixLen
返回 base + px2fp(addPx)
```

- 实测宽按 `字号|字体|字重|字距|文本` 缓存（上限 4000，超了整体清空）
- 段末行 / 标题行不补偿（自然长度）
- `EngineLine` 新增 `widthPx`（SDK `LineMetrics.width`，`@ohos.graphics.text.d.ts`，@since 12：
  「Width of a line, in physical pixels (px).」）—— 当前仅上下档早期版本用过，**可评估删除**

### 附带修掉的两个真 bug

1. **上下档 `fontSerial` 缺 `@Watch`**：改字号不重算引擎行 ⇒「用新字号画旧断行」。
   实测特征：字号 34fp→12fp 后，行仍按 34fp 容量断（19 字/行），却用 12fp 画 ⇒ 每行只占 1/3 宽。
2. **上下档引擎宽改用容器实测宽**（`onAreaChange` → `containerWpx`），并在尺寸变化时重排；
   原实现取 `display.getDefaultDisplaySync().width`（整机屏宽），横屏/分屏会断错行。

### 真机确认

- 上下档：用户确认「不偏移了」✅
- 无动画档：行尾补齐确认过，但**随后发现底部溢出**（见 §三）

## 三、未收口：无动画档底部溢出（**接手重点**）

### 现象（截图 `_dsh_shots/2026-11-05-detect/noanim-overflow.jpeg`）

dump 实测最后一行 `y=[2813-2848]` 被屏幕底边裁掉（屏幕高 2848），即**多出一行**。

### 已尝试 + 结果

| 尝试 | 结果 |
|---|---|
| 补偿量留 2px 余量 | 仍溢出 |
| `measureText` 补 `fontWeight` | 已改（未最终验证） |
| 回退无动画档补偿 | 操作被中断，**工作区状态需先确认** |

### 两个可疑源头（需用数据分开，**不要再盲改**）

- **A. 行高口径不一致（结构性，一直存在）**
  分页 `paginateLines()` 用 `LineMetrics.height` 累加；渲染用 `Text(...).lineHeight(lineHeightFp)`。
  两者不等 ⇒ 必然溢出或底部空白。
  **测法**：dump 每行 `bounds.y` 步进，与 `lineHeightFp × 密度` 比较；再比 `行数 × 步进` 与 `areaH × 密度`。
- **B. 字距补偿把行撑到临界**（本轮新增）
  补偿后"实测宽 + 补偿"≈ 可用宽，差 1px 就折行 ⇒ 整页多一行。

### 结构性防线（建议一并加，成本极低）

给每行 `Text` 加 **`maxLines(1)`**（配合 `textOverflow`）：
**从物理上杜绝"折行导致整页多一行"**，把 B 这条线一次排除；剩下的必然是 A。

### 对照参考（用户提问的答案）

ReaderKit 不会溢出，因为它是**单一引擎**：分页与渲染是同一次排版，页面高度由容器给定。
我们溢出的结构性原因是「**算一套、画一套**」——这是自研方案的固有代价。

### ⚠️ 真机实测的 SDK 坑（真机实测 > SDK 声明，已记档）
`TextLine.paint(cv, x, y)` 文档写「(x,y) = 行框左上角」（`@ohos.graphics.text.d.ts:3355-3364`），**实际字形落在 `painted + 段内自然位置`** —— 逐行累加行高绘制会得到 2:1 交替错乱行距（截图 `poc-C.png`）。改用整段 `Paragraph.paint`（段落顶 = (x,y)，标准语义）+ 裁剪后正常。落位算式自消去：段落顶 = `glyphTop − natY(k1)`，与 natY 取值无关。

### A/B 对比（同页 1336/9898，36fp/行距1.2，手机）
- **断行**：13 行逐字一致（run 匹配 `ok=3` 零失败，k1 定位正确，页首段中行 k1>0 也命中过）
