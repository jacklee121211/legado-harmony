## 3. 四步实施

### 第一步（基础）：适配数据结构，统页边界

**⚠️ 不要搬基座的分页算法。** 核实结论：

| | 基座 `NovelContentParseHelper` | 我们的 `ReaderPager.paginateNodes` |
|---|---|---|
| 每行字数 | `floor(宽/字宽)` | `floor(areaW/fontSize)` |
| 每页行数 | `floor(高/字高)` | `floor(areaH/lineHeight)` |
| 切行 | `I18n.getLineInstance('cn')` | 同 |
| measure 调用 | 0（`HL_ADVANCE_RATIO=1.0` 估算） | 0 |

**算法已经同构了。** 差的是**产出结构**：

基座消费者只认（`ReaderChaptersItem.ets:19-30`）：
```ts
class ReaderChapterPageItem {
  startIndex: number
  endIndex: number
  lineContentList: string[]
  get content(): string { return this.lineContentList.join(''); }
}
```

我们产出 `PaginateResult { pages: number[][][], pageOfNode: number[], pageLines: string[][] }`。

**做法**：加一层纯函数适配
```ts
// ReaderPager 里新增（或独立文件）
export function toChapterPageItems(res: PaginateResult): ReaderChapterPageItem[]
// pages[p] → 该页段切片；pageLines[p] → lineContentList
// startIndex/endIndex 按累计字符数算（基座 configProvider.ets:84-89 同款）
```

**不要做的**：
- ❌ 不引入基座的 `ReaderProvider` → `ReaderConfigProvider` → `ReaderSourceProvider` 那段 `@Provide/@Consume` 链
- ❌ 不引入 `taskPool`（我们的算法已经够快，整章 0 次 measure）
- ❌ 不改 `paginateNodes` 本身（它是无动画和沉浸层共用的已验证实现）

### 第二步（横滑）

基座 `readerLibrary/src/main/ets/view/SlideFlipView.ets`（82 行）原样搬。

**关键改动只有一处**：里面的 `Reader` 组件（`Reader.ets:9-59`）加可选参数
```ts
@Prop hlFrom: number = -1;
@Prop hlTo: number = -1;
```
渲染时若有高亮区间 → `Text() { Span×3 }`，否则单个 `Text(content)`。

**高亮天然有，不需要切换模式。**

### 第三步（仿真）

基座 `readerLibrary/src/main/ets/view/SimulateCurlView.ets`（214 行）原样搬。

**关键事实**（`SimulateCurlView.ets:153-158`）：
```ts
ReaderForCurlView({ content: ... })
  .visibility(isOnGesture || isOnAnimation ? Visibility.None : Visibility.Visible)
```
**仿真的静止层本来就是 ArkUI `Text`，不是 Canvas。** Canvas 只在手指按下 / 动画中接管。

所以给 `ReaderForCurlView`（`Reader.ets:62-142`）同样加 `hlFrom/hlTo` 即可。

**代价**：手指按下到松手那约 300ms 卷曲动画中，Canvas 画不了 `Span` ⇒ 暂时没有高亮。
**这是可接受的**（用户不会注意）。不要为了它去 Canvas 里 `drawRect`（成本高，不做）。

### 第四步（TTS 高亮接线）

## 4. 三条硬约束（违反必然崩，每一条都踩过）

### 约束 1：几何来源必须统一

基座几何来自 `Text.onSizeChange`（`.layoutWeight(1)` 撑满后的真实盒子），边距写死 `SCREEN_MARGIN_LEFT=20`。
我们用标定值 `calibTopPx` / `calibWidthRatio` / `effectiveLineMul`。

**两套几何 ⇒ cpl 不同 ⇒ 页边界不同 ⇒ 切档还是跳。**

⇒ **统一用我们的标定值**，把基座的 `padding: { top:20, bottom:20, left:20, right:20 }` 换成
`sideInsetVp` / `topInsetVp` / `bottomInsetVp`（来自 `ReaderPage3.textAreaLeftVp()` / `scrollTopInsetVp()` / `scrollBottomInsetVp()`）。

### 约束 2：高度约束**不能**用 `layoutWeight(1)`

SDK 原文（`common.d.ts:17456`）：
> 「The **remaining space** on the main axis is then allocated proportionally among elements with a `layoutWeight` value greater than 0」

基座的 `Column > Text(.layoutWeight(1)) + ReaderBottom()` 里，`ReaderBottom` 是**兄弟节点**，所以成立。
**我们没有那个兄弟 ⇒ 必须 `.height('100%')`。**

违反 = 真机「内容只有上半屏」。

### 约束 3：背景画在**页组件自己身上**

基座 `Reader.ets:49`：`.backgroundColor(this.bgColor)` 在页 `Column` 上。
页翻到哪底色跟到哪。

**不要**在父层垫一层不透明背景再让子层也画一层 ⇒ 会盖住背景图（真机「只识别文字颜色，背景不行」）。

## 5. 历史教训（我的误导，必须避开）

| # | 错误说法 | 事实 |
|---|---|---|
| 1 | 「照基座抄」然后重写分页 | 基座分页和渲染是**配套**的，拆开各改一半必然对不上 |
| 2 | 上下和无动画「机制相同」 | 上下是流式 `List`，无动画是**切页**。同源的是**版式参数**，不是机制 |
| 3 | `measureTextSize` 返回值当 vp | **入参 vp，返回值 px**。差 density(≈3.375) 倍 |
| 4 | `layoutWeight(1)` = 撑满 | 它分的是**剩余空间**，需父容器高度确定 + 有兄弟节点 |
| 5 | 自己发明分页算法（量整段循环） | 整章几千次 measure ⇒ 卡死。基座整章 **0~1 次** |
| 6 | 「要做高亮所以必须重写渲染层」 | **错**。高亮靠 `Span`，按段渲染就能做，与分页无关 |
| 7 | 用 PowerShell 拼字符串改 .ets | `Set-Content -Value ($a+$b)` 吞换行，把文件写坏 |
