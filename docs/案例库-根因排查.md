## 二、案例 1：折叠/展开后阅读页消失、进度回退（2026-11-06）

### 症状
- 外屏 → 内屏（展开）后停在书架，进不去书
- 偶发"打开失败"
- 进度被重置到更早的位置

### 观测集（关键在第 3 条）
1. 必现：展开后停在书架
2. 偶发：有时能接续成功
3. **成功那一次的区别**：用户点了外屏卡片「继续阅读」= **阅读页当时已经在栈上**

### 假设表（我最初只填了后三行，漏了第一行 —— 这就是全部差距）

| 假设 | 一步证伪 | 结果 |
|---|---|---|
| **谁主动删了页面**（pop/close/退出） | `grep 'AppRouter\.pop'` + 日志搜 `isPopPage` | ✅ **成立**：`ReaderPage3.registerScreenDensityChange()` 密度回调里 `AppRouter.pop()`（**当时**行号 5437，现为 `L5490` 守卫 → `L5505` pop；行号已漂移，以原文为准） |
| 页面被重建（生命周期） | 日志里同一本书 `startPlay` 出现几次 | ✅ 两次（是"被 pop 后重建"的**结果**，不是原因） |
| 条件渲染换树 | 查 build 根部 `if(outerMinimal)` | 部分成立（书架换卡片），但解释不了"进度回退" |
| 异步落盘竞态 | 打"读到的值" | ✅ 成立（重建时读到旧磁盘值）—— 但同样是**结果** |

### 分裂实验（一步定生死）
```
日志搜 isPopPage → 22:37:55.494 display mode is changed → 55.564 isPopPage:1（无来源 pop）
→ 22:37:58.743 pop、22:38:04.339 pop：三次切换全部有无来源 pop
→ grep 'AppRouter.pop' 全仓只有一处命中密度回调
→ git blame 该行 → faf05ec（2in1 跨 DPI 兜底）
→ 密度实测：外屏 3.0 / 内屏 2.55（rs-migrate 55.889）→ 每次开合必跨
```

### 根因一句话
`ReaderPage3.registerScreenDensityChange()` 在**密度变化**时执行 `AppRouter.pop()`，
而折叠屏每次开合必然跨密度 ⇒ **每次折叠都退出阅读页**。

### 排除证据
- 若是"接续逻辑没写"：没法解释 `isPopPage:1` 这条系统日志；
- 若是"进度没保存"：没法解释"阅读页两次 `startPlay`"；
- 只有"每次折叠 pop 一次"能同时解释：停在书架（被 pop）、偶发成功（竞态赢了）、进度回退（重建读旧磁盘）。

### 可迁移的教训
**"东西消失了"先找"谁删的"，不要先找"怎么补回来"。**
以及：**成功样本与失败样本的差异量，往往就是根因所在的变量。**

### ⚠️ 行号复核（2026-11-06 二次核对，必读）

本案例写于修复前后，**行号已随重构漂移**，引用时必须连原文一起引用：

## 三、从案例抽出的通用提问清单（换任何 bug 都能问）

> 这十条是"思维逻辑"，不是某个项目的事实。按**信息增益**排序：越靠前，一问越可能直接定死。

1. **谁主动让这件事结束了？**（pop / close / clear / release / destroy / stop / reset / cancel）
2. **成功那次和失败那次，差哪个量？**（时间差、状态差、环境差、入口差）
3. **这条路径上，有哪些"环境自变量"在偷偷变？**（密度、尺寸、断点、折叠态、缩放、深浅色、语言、电量策略）
4. **我依赖的那个值，是谁改的？改的时机在哪？**（写入口唯一吗？异步吗？）
5. **这东西被创建了几次？被销毁了几次？**（同一日志里数 Enter/Exit）
6. **它是"没做"，还是"做了又被撤销"？**（这两类的修法完全相反）
7. **这段代码是哪一年为哪个环境写的？现在那个环境还在吗？**（`git log -S` / `blame`；兜底代码是头号嫌疑人）
8. **系统/框架自己说了什么？**（先搜框架日志，再搜自己埋的词）
9. **我的假设被哪条观测证伪过？**（主动找反证；找不到反证 ≠ 假设成立）
10. **如果我现在改代码，改完之后我能不能一句话说出根因？**（说不出 = 还没定位）

### 三条排序法则（决定先做哪个实验）
- **便宜优先**：一条 grep / 一条日志能定的事，绝不先去改代码跑真机
- **分裂优先**：选那个"结果 A 就排除一半假设、结果 B 就排除另一半"的实验
- **机制层优先**：同样成本下，探针埋在路由/生命周期/环境层，而不是排版/渲染层

## 四、反例库：本项目"看起来是原因、其实不是"的坑

> 每条都是**真实发生过**的误判，用来防止再次走进去。

| 误判 | 当时以为 | 实际 | 教训 |
|---|---|---|---|
| 书架底部灰白横条 | `linearGradient` 重复着色 | HDS 页签自带的 `gradientMask` 蒙层（官方默认值） | "我画的"之前，先想"系统叠了什么" |
| 折叠接续 | 页面被重建（改去补重试/进度） | 密度回调里的 `AppRouter.pop()` | 先找"谁删的" |
| 大字号行尾留白 | 亚像素临界（差 0.9px 吞一个字） | 两套引擎度量差 + 逐行补偿错误 | 一个假设解释不了**全部**字号档，就不成立 |
| 大字号排版异常 | 时序分叉（引擎新/渲染旧） | 一半是渲染侧陈旧行（`fontSerial` 缺 `@Watch`），一半是版式常量 | 分档、分设备取证，别用一个样本推全体 |

**共同点**：四次误判都发生在"**我先有了一个合理故事**"之后。合理的解释 ≠ 证据。
