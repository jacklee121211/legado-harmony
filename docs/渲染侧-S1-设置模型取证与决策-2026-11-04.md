# 渲染侧 S1 取证与决策（2026-11-04）：设置模型走 A 路还是 B 路

> 用户口径（2026-11-04）：「既然都要做了就彻底一点，我们追求的不是最小实现，而是真正一个一劳永逸的架构跃迁。」
> 本文**只做取证与决策**，不改任何代码。结论在 §4，证据原文逐条可核。

## 1. 问题：设置模型的状态载体选哪条路

| 路 | 载体 | 优点 | 风险 |
|---|---|---|---|
| A | 普通 class 实例 + 页面保留 `@State` 引用（模型内部字段是普通字段） | 改动小、刷新语义不变 | 模型本身不是响应式；细粒度刷新仍靠页面 `@State` |
| B | `@ObservedV2` + `@Trace` 的模型 | 属性级观测、深度观测、可单测 | 与 V1 混用受限；有实证的陷阱（见 §3） |

## 2. 取证：官方原文（`devecocli docs read`）

### 2.1 `@ObservedV2`/`@Trace` 本体限制
documentId `开发指南/…/状态管理_V2/…/arkts-new-observedv2-and-trace`

```
*   @ObservedV2装饰器与@Trace装饰器需要配合使用，单独使用@ObservedV2装饰器或@Trace装饰器没有任何作用。
*   被@Trace装饰器装饰的属性property变化时，仅会通知property关联的组件进行刷新。
*   未被@Trace装饰的属性用在UI中无法感知到变化，也无法触发UI刷新。
*   @ObservedV2仅能装饰class，无法装饰自定义组件。
*   @Trace不能用在没有被@ObservedV2装饰的class上。
*   @Trace是class中属性的装饰器，不能用在struct中。
*   使用@ObservedV2与@Trace装饰的类**不能和@State等V1的装饰器混合使用，编译时报错**。
*   @ObservedV2与@Trace装饰器从API version 12开始支持。
```

### 2.2 V1/V2 混用指导（API 19 及之后）
documentId `…/状态管理V1和V2混用场景/…/arkts-v1-v2-mixusage`

```
#### 限制条件
1.  V1装饰器不能和@ObservedV2一起使用。因为@ObservedV2/@Trace有自己独立的观察能力，不仅可以在@ComponentV2中使用，
    也可以独立在@Component中使用，状态管理框架不希望其观察能力和V1的观察能力混合使用，所以依旧维持禁止现状。
2.  V2->V1，V1不支持用装饰器接收@ObservedV2装饰的class，否则编译报错。
3.  V1中@Link遵循其原本初始化规则，只能被V1状态变量初始化…
```

同文档又给出两个**官方后门**：

```
#### makeV1Observed
makeV1Observed将不可观察的对象包装成状态管理V1可观察的对象，能力等同于@Observed，其返回值可初始化@ObjectLink。
限制条件：不支持@ObservedV2、makeObserved 的返回值…

#### enableV2Compatibility
enableV2Compatibility将V1的状态变量使能V2的观察能力，即让V1状态变量可以在@ComponentV2中观察到变化。
限制条件：不支持@ObservedV2、makeObserved 的返回值…
```

## 3. 关键判断（逐条给依据）

### 3.1 **页面可以持有一个 `@ObservedV2` 模型实例，但不能用 `@State` 装饰它**

依据 §2.2-1：`@ObservedV2/@Trace … 也可以独立在@Component中使用`（即 V1 组件里**可以直接用**，只要不套 V1 装饰器）。
依据 §2.2-2：反过来「V1 用装饰器接收 V2 class」才编译报错。
⇒ 页面写 `private model: ReaderSettingModel = new ReaderSettingModel(...)`（**不加 `@State`**），
   UI 里 `this.model.fontSize` 读值，改值由 `model` 的 `@Trace` setter 触发刷新。**这条路是官方支持的**。

### 3.2 但**不能**把模型实例直接落盘 —— `__ob_` 会污染既有设置（本工程有前科）

**本工程设置是怎么落盘的（实测取证，不是推测）**：

| 位置 | 写法 | 证据 |
|---|---|---|
| 阅读设置 | `PreferencesUtil.putSync(\`ReaderSetting_${nm}\`, this.readerSetting)` | `ReaderPage3.ets:3284`、`:4150` |
| 背景/方案记录 | `PreferencesUtil.putSync(key, JSON.stringify(rec))` | `ReaderCustomBg.ets:618`；读取 `JSON.parse` `:606/:661/:776` |
| 传书/对齐载荷 | `JSON.stringify(payload)` | `ReaderPage3.ets:4840` 等 |

`PreferencesUtil.putSync` 只是转调平台 `preferences.putSync(key, value)`（`oh_modules/…/harmony-utils/src/main/ets/utils/PreferencesUtil.ets:79-82`），
`value` 类型是 `preferences.ValueType`（含 object）⇒ **序列化发生在平台侧**，本工程对这一步**没有控制权**。

而官方 FAQ 明确（documentId `FAQ/UI框架/组件使用/ObservedV2与_Trace装饰的对象key都带有_ob_导致反序列化异常/faqs-arkui-1587`）：

```
@ObservedV2与@Trace装饰的对象key都带有__ob_导致反序列化出现异常，无法反序列化。
状态管理V2装饰器会为装饰的变量生成getter和setter方法，同时为原有变量名添加__ob_的前缀…
```

**这条路径已经出过一次事故**（代码自述，`ReaderPage3.ets:4133-4144` 原文）：

```
//        ② 这里做类型体检，读到的不是"带 fontSize/lineHeight 的对象"就
//          **丢弃并用默认值重建**，让已被污染的书自动恢复。
...
        'readerSetting 持久位类型非法（推测是接续旧版污染），已丢弃并重建默认值。book=%{public}s',
```

⇒ 若把 `@ObservedV2` 实例直接交给 `putSync`，极可能写出带 `__ob_` 的键，**老用户设置全坏**（历史上已经坏过一版）。
虽然上述 FAQ 取证的是 `JSON.stringify`/`getTarget` 路径，**平台侧对 object 的序列化是否同样受影响尚无直接原文**（标【待验证】），
但本方案**不需要它成立**：模型一律经纯函数 `toRecord()` 转成普通对象后再落盘，风险从设计上消除。

⇒ 模型必须**拆两层**：`@Trace` 的**响应式模型** + 纯函数 `toRecord()/fromRecord()` 负责序列化（只吐普通对象）。

### 3.3 影响面：`this.readerSetting` 在 `ReaderPage3` 里出现 **259 次**
（本次实测 `Select-String -Pattern 'this\.readerSetting' -AllMatches` = 259）
⇒ B 路不是"改一个字段"，是**改动 259 个读写点**，且其中包含 `setPageConfig(this.readerSetting)`
（`readerCore.ReaderSetting` 是 ReaderKit 的接口类型，**必须**在交付给引擎前转回纯对象）。

### 3.4 本工程目前 **0 处** `@ObservedV2`/`@Trace` 用法
（`entry/src/main/ets/**` 全量 grep = 0）⇒ B 路没有任何先例可抄，属"首次引入新机制"，须按工程铁律**可一键回退**。

## 4. 决策

**走 B 路，但采用「双层 + 单点适配器」结构**（既彻底又不炸老数据）：

```
ReadSettingState（@ObservedV2 + @Trace）      ← 唯一可变真源，细粒度刷新
        │ toRecord() / fromRecord()（纯函数）
        ▼
readerCore.ReaderSetting（纯对象）            ← 只在 setPageConfig / 落盘 的边界出现
```

- 页面：`private settingState: ReadSettingState = new ReadSettingState()`（**不加 `@State`**，依据 §3.1）；
- 259 个读写点分批迁移，**迁移期保持 `readerSetting` 作为"投影"存在**（由 `settingState` 单向派生），
  这样每一批都能单独构建+真机对照，任何一批出问题只回退该批；
- `setPageConfig(x)` 的入参一律走 `settingState.toRecord()`，**绝不允许把 `@ObservedV2` 实例直接传给引擎或 `JSON.stringify`**（依据 §3.2）。

**不可接受的做法**（会踩上文证据）：
1. 给模型字段套 `@State`（§2.1/§2.2-1 编译报错）；
2. 把模型实例直接 `JSON.stringify` 落盘（§3.2 写出 `__ob_` 脏键）；
3. 把模型实例直接传给 `setPageConfig`（引擎要纯接口对象）。

## 5. 分步（S2 起，每步独立可回退）

| 步 | 内容 | 验收 |
|---|---|---|
| S2-a | `ReadSettingState` 类 + `toRecord/fromRecord` 纯函数；**不接管任何 UI**，只把现有 `readerSetting` 的初始值同步过去 | P5 单测：默认值逐字段相等；`toRecord` 不含 `__ob_` 键（断言 `JSON.stringify(rec).indexOf('__ob_') === -1`）；`fromRecord(toRecord(x)) === x` |
| S2-b | 页面加投影：`private get readerSetting()` 改为从 state 派生（或保留字段 + 单向同步），259 个读点**先不动** | build + 7 闸门 + 真机：字号/行距/主题/材质全量 A/B 节点差异 0 |
| S2-c | 分批把**写点**改到 `settingState`（按测绘的区块顺序：外观→字体→排版→标定） | 每批：写后引擎下发**一次**（日志可数）+ 落盘记录不含 `__ob_` |
| S3 | `ReaderSettingActions`：把 15 个 handler 的副作用集中 | 每个设置项只产生一次 `setPageConfig` |
| S4 | 面板区块组件化（沿用 R-1 的严格 A/B 流程） | 每块节点差异 0 |

## 6. 风险与回退

- 风险最大的两处：**首次引入 `@ObservedV2`**、**259 个读写点**。故 S2-a 不接管 UI（纯新增），S2-b 保持投影（单向），
  任一阶段出问题 `git revert` 该提交即恢复到"页面 `@State readerSetting` 原样"。
- 设备侧已有设置数据（`ReaderSetting_<书名>` 等 Preferences 键）**不得被改写**；
  验证手段：改造前后各拉一次 Preferences 快照对比（含"不含 `__ob_`"断言）。
