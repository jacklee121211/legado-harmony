## 0. 一句话

把阅读页与主页的**固定外观元素**（阅读区、上下留白带、信息条底板、dock 图标、minibar 图标）
注册成一张「元素表」；每个元素可挂**皮肤**（代码着色 / 图片素材 / 自定义 symbol 字体），
**逐元素缺省回落**到当前默认外观——天然支持"整体皮肤"与"单独皮肤"并存。

## 1. 背景与动机

1. 2026-11-05 为对齐验收加了「正文绝对显示区」调试浮层
   （`ReaderPage3.ets` 的 `DebugTextAreaOverlay()`，开关 `SET_READER_TEXT_AREA_DEBUG`，
   位于 我的-设置 → 听书引擎（进阶））。
2. 用户用它核对了三台设备的覆盖情况后提出：这个"定位机器"不应该只服务调试，
   应该泛化成**主题系统**——区域就是元素，元素就能穿皮肤。
3. 现有主题系统只有双色（`ThemeItem{mainColor, secondColor}`，`ThemeManager.ets`），
   **没有资源维度**。本设计是它的扩展，不推翻它。

## 2. 实测基准（2026-11-06，三台设备 36 张截图逐像素测量）★所有数字的来源

> 方法：截图里调试浮层是 80% 透明红 + 1vp 红边，可编程精确检出矩形边界；
> 正文墨迹按背景极性自适应阈值检出。脚本与阈值见 §2.5，逐张原始数据见 CSV。

### 2.1 设备与密度

| 设备 | 截图分辨率 | 密度(px/vp) | 证据 |
|---|---|---|---|
| Mate80 Pro+（m80pm） | 1320×2848 | 3.375 | `ReaderCalibMath.ets:330`（手机 3.375） |
| Pura X 内屏（purax） | 1320×2120 | 2.55 | 同上（宽折叠 2.55）；实测反推一致（224px÷2.55=87.8vp=88） |
| 12.2 平板 | 竖 1840×2800 / 横 2800×1840 | 2.25 | 同上（平板 2.25） |

517.6×831.4vp **不一致**【待验证】——两者差固定倍率 1.176，疑为当时用了别的 vp 基准。
主题系统不依赖它，但别拿 440×707 当窗口真值用。

### 2.2 调试矩形 = 模型，三台双方向全部逐像素命中

模型（单一真源，**皮肤必须调用这些函数、禁止抄数字**）：

- 上边 = `scrollTopInsetVp()` = 88vp（`ReaderCalibMath.ets:374-377`，常量 `:104-105`）
- 下边 = 屏高 − `scrollBottomInsetVp()` = 屏高 − 62vp（`:394-397`，常量 `:112`）
- 左右 = `textAreaLeftVp()` / 宽 = viewPortWidth × calibWidthRatio(0.861)
  （`:406-412`；`HL_DEF_WIDTH_RATIO=0.861` 在 `ReaderConst.ets:62`）
- 浮层挂 `.scale(READER_ZOOM=1)`（`ReaderPage3.ets:1731`、`:357`）——当前为 1，但钩子要保留

实测（信息条关状态，纯矩形）：

| 设备/方向 | 矩形 rows (px) | 上留白换算 | 下留白换算 | 矩形 cols (px) | 宽度比例 |
|---|---|---|---|---|---|
| m80pm | 297..2638 | 88.0vp | 62.2vp | 92..1228 | 0.861 |
| purax | 224..1961 | 87.8vp | 62.4vp | 92..1228 | 0.861 |
| 12.2 竖 | 198..2660 | 88.0vp | 62.2vp | 128..1711 | 0.861 |
| 12.2 横 | 198..1700 | 88.0vp | 62.2vp | 195..2605 | 0.861 |

**结论：上下留白 88/62vp 与宽度比 0.861 跨机型、跨方向恒定。**
「留白带高度恒定 vp、宽度随机型拉伸」的皮肤适配模型成立。

### 2.4 正文墨迹 vs 矩形（信息条关组 = 唯一干净测量）

| 设备/方向 | 模式（截图自带徽标对号） | 墨迹范围(px) | 判定 |
|---|---|---|---|
| m80pm | 仿真 / 上下 / 无动画 三档全部 | 95..1216 | 全部贴合矩形（92..1228） |
| purax | 无动画 / 上下 / 仿真 | 94..1217 / 94..1218 / 110..1209 | 全部贴合 |
| 12.2 竖 | 仿真 / 上下 / 无动画 | 128..1711 / 127..1711 / 128..1711 | 逐像素贴合 |
| **12.2 横** | **横滑（ReaderKit）** | **161..2638** | **每侧超出 34px = 15.1vp ≈ 0.6 字** |
| 12.2 横 | 上下 / 无动画 | 192..2605 / 195..2605 | 贴合 |

要点：

1. **12.2 横屏 × ReaderKit 横滑是 36 张里唯一的超宽**：实际宽度比 0.8846
   （水平边距 161.5px = 71.8vp），模型按 0.861（边距比例 6.95%）假设。
   左右对称溢出（裁剪图 L3-012015-left/right 可目视确认）。
2. 平板横屏**没有仿真档**，自动退横滑（`ReaderPage3.ets:5796-5797` 原文：
   「平板横屏没有仿真档）⇒ 退到横滑」）——所以 12.2 横屏的 ReaderKit 档=横滑，
   徽标实测与代码一致。
3. 「仿真 = 横滑同位」的说法**数据支持**：仿真存在的三处（m80/purax/12.2 竖），
   仿真 = 矩形 = 自绘逐像素同位。横屏超模是 **RK 在宽屏横版的水平边距行为偏离了自己
   在竖屏的比例**，不是"仿真≠横滑"的分歧。
4. 信息条可见组测得的"越界墨迹"（如 inkMin=45）是**信息条自己的图标**
   （时间/月亮在左、眼睛/页码在右，行 padding 左右 20vp），不是正文溢出——测量时要排除。
5. m80/purax 截图是深色主题、12.2 是浅色主题——墨迹检测必须按背景极性自适应（§2.5）。

### 2.5 测量方法与复现（下次直接用，不要再摸索）

产物目录（仓库外）：`D:\Arkts\3.8.11\_dsh_shots\20261106-主题标定对比\`

- `rect-measure-v3.csv` —— 每张图的 矩形边界/背景亮度/墨迹范围
- `badge-sheet2.png` —— 36 张截图底部模式徽标拼表（对号入座用）
- `L1-011805-*.png`、`L3-012015-*.png` 等 —— 边缘裁剪图（目视验证溢出）
- `measure-v3.ps1` / `badges2.ps1` —— 测量脚本（PowerShell + 内联 C#）

算法要点（v3，已验证可复现）：

1. 红像素判定：`R−G>40 && R−B>40 && R>110`（JPEG 色漂下稳定）；
   行阈值 ≥3%×W、列阈值 ≥10%×矩形高 → 矩形 rows/cols。
2. **必须用 `LockBits` + 内联 C#**（Add-Type），PowerShell 逐像素循环慢 100 倍以上。
3. **脚本文件必须带 UTF-8 BOM**：中文 Windows 的 PowerShell 按 GBK 读无 BOM 脚本，
   中文路径直接变乱码报错（本项目踩过：提交钩子日志乱码同源）。
4. 背景极性自适应：采样矩形左外侧列的中位亮度 bgLum；bgLum<128 判深色主题，
   墨迹=亮度>bgLum+120；浅色主题墨迹=亮度<110。
5. **信息条可见时，扫描带内会混入信息条图标**（行 padding 20vp 处）——
   干净测量只看"信息条关"组；或把扫描带限制在模型矩形 rows 内缩 25px。
6. 截图底部中央的**模式徽标**（仿真/横滑/上下/无动画）是模式对号的唯一可靠依据，
   裁 `W/2−260, H−300, 520×240` 即得。

### 2.6 顺带发现的遗留对齐问题（只记录，未修，另行开工）

12.2 横屏下 RK 横滑每行比自绘宽 ~1 字（0.8846 vs 0.861）→ 横屏两层断行系统性错位
（竖屏是 ±1 字物理极限，横屏是**固定 +1 字**）。修复方向：给 `calibWidthRatio` 增加
**横屏档**（自绘向 RK 对齐，0.8846 起标）——但改前必须真机验证 RK 对 viewPortWidth
变化的响应（参考 AGENTS.md §8 的 viewPort 旧值坑）。**主题系统的"阅读区框"冗余量
必须 ≥ 16vp 才能同时盖住两种档位**（15.1vp < 16vp）。

## 4. 皮肤包格式（规范核心二）

### 4.1 manifest JSON（草案，formatVersion 起步为 1）

```json
{
  "formatVersion": 1,
  "id": "sunset-paper",
  "name": "晚霞纸",
  "author": "…",
  "elements": {
    "reader.band.top":        { "type": "image", "asset": "band_top.png",
                                "stretch": { "slice": { "top": 24, "right": 24, "bottom": 24, "left": 24 } } },
    "reader.band.bottom":     { "type": "image", "asset": "band_bottom.png", "stretch": { … } },
    "reader.text.frame":      { "type": "image", "asset": "frame.png", "insetExtraVp": 16, "stretch": { … } },
    "reader.text.fill":       { "type": "code", "color": "#FFF8EC" },
    "reader.infobar.bg.top":    { "type": "image", "asset": "infobar_top.png" },
    "reader.infobar.bg.bottom": { "type": "image", "asset": "infobar_bottom.png" },
    "dock.icon.shelf":        { "type": "svg", "asset": "shelf.svg" }
  },
  "dark": {
    "reader.text.fill": { "type": "code", "color": "#3A2A28" }
  }
}
```

规则：

1. **逐元素缺省回落**：manifest 里没写的 key = 用当前默认外观。这是"整体皮肤 /
   单独皮肤并存"的实现点，不要另做开关矩阵。
2. `dark` 段可选：深色档优先取 `dark[key]`，没有再回落 `elements[key]`，再回落默认。
3. `stretch.slice` = 九宫格参数（vp，`Image.resizable({slice: EdgeWidths})`，
   SDK `image.d.ts:1950-1965`，`@since 11`，单位 vp 原文「The default unit is vp」）。
   纹理类素材可省略 slice 走整体拉伸；纯色/渐变直接 `type:"code"` 零素材。
4. 图标 key 的 asset 解析：
   - `symbol-ttf`：整包注册制，见 §6，manifest 里写 `"glyph": "0x100016"` 映射；
   - `svg`：`Image($rawfile(...))` 或导入文件的 `file://` 路径，fillColor 走主题色。
5. `insetExtraVp` 只对 `reader.text.frame` 合法（四周向外扩多少）。

### 4.2 素材通道三型（为什么是这三个）

| 通道 | 适用 | 实现 | 限制 |
|---|---|---|---|
| `code` | 纯色/渐变 | backgroundColor / linearGradient | 零素材、零体积，永远可用 |
| `image` | 纹理/框图/底板 | Image 组件（slice 九宫格或整体拉伸） | PNG **不可染色**（fillColor 不生效，`Index.ets:1864-1866` 注释原文：「PNG 的 fillColor 不生效，色值烧死在图里」）→ 需要随主题变色的一律 SVG |
| `symbol-ttf` | 图标族 | `symbolRegister.registerSymbol(ttf, json)` | 整包注册；尺寸限额（错误码 1012600002/3）；见 §6 |

### 4.3 素材设计规范（写给作图的人）

1. **带四角/边缘装饰的框图必须按九宫格设计**：四角=固定区，边=拉伸区，
   中心=可拉伸安全区。2in1 横屏宽度可达 2800px+（拉伸比 ~2.4×于 m80），中间安全区必须
   经得住拉。
2. **阅读区框四周冗余 ≥16vp**（`insetExtraVp` 默认 16）：盖住 12.2 横屏 RK 横滑 15.1vp 的
   实测偏差（§2.6），且圆角不得压首尾行墨迹。
3. 信息条底板：贴边方向按上/下两态各出一套；行高按 18vp 设计、上下呼吸区按 §2.3 公式。
4. 深色档：要么出 `dark` 变体，要么选深浅通用素材。
5. 最小画布（Pura X 外屏 326×326vp）：四角固定区合计 ≤ 画布短边的 1/3。

### 4.4 存放与导入

- **内置皮肤包**：`resources/rawfile/skins/<id>/`（manifest.json + 素材）。
  rawfile **没有目录列举 API** ⇒ 用索引文件 `rawfile/skins/index.json` =
  `{"packs":["<id>",…]}` 列出全部内置包 id；`SkinStore` 启动时按索引逐个加载
  （实现于 P2.1，2026-11-06）。任一 manifest 缺失/损坏/版本不匹配 ⇒ 跳过该包，
  内置 code 包兜底，不抛错不崩。
- **用户导入包**：沙箱文件目录；`image`/`svg` 通道直接支持 `file://` 路径；
  `symbol-ttf` 通道**能否接受沙箱路径待验证**（`registerSymbol` 签名收
  `resourceManager.Resource`，SDK `@hms.hds.symbolRegister.d.ts:24-35`；
  官方指南只演示了 `$rawfile`。验证前：导入包的图标通道降级为 svg）。
- 存取沿用 `PersistentStorage` + 字符串 JSON 的既有路子（`ThemeManager.init()` 同款）。

## 5. 层序口径（规范核心三）★先钉死，防"书架横条"式层序事故重演

### 5.1 阅读页 z 序（从底到顶）

```
① 整页背景（ReaderKit themeColor / themeBgImg —— 引擎自渲染）
② 留白带皮肤（reader.band.top / bottom）
③ 阅读区框 + 芯（reader.text.frame / fill）
④ 三层正文（ReaderKit / 自绘上下 / 自绘无动画 —— 现状不动）
⑤ 信息条底板（reader.infobar.bg.*）
⑥ 信息条内容（时钟/电量/书签/防窥/页码 —— 现状不动）
⑦ 调试浮层（DebugTextAreaOverlay 现位，ReaderPage3.ets:1719-1723）
⑧ 菜单/弹窗/设置面板（现状不动）
```

要点与理由：

- ②③⑤⑥ 全部 `HitTestMode.None`（调试浮层同款，`:1732` 已验证不挡翻页/点按）。
- ②③ 挂在三层正文**之后、「正在排版…」占位之前**的同一槽位（即调试浮层现在的位置）；
  保留 `.scale(READER_ZOOM)` 钩子（当前 =1）。
- **带区（②）画在引擎 surface 之上是安全的**：带区按定义无正文（insets 的定义就是
  「正文不进这里」，官方 FAQ `faqs-reader-3`：ReadPageComponent 顶部底部预留页眉页脚）。
  这是整套方案不碰 ReaderKit 的立足点。
- 仿真翻页时页面（含背景）会卷起，而 ②③ 是 ArkUI 层不跟着卷——表现为"页面拿走、
  桌布留下"。这是**接受的行为**（也是方案 A 的定义）；若将来要"皮肤跟页面一起卷"，
  走 §5.2 方案 B。

### 5.2 阅读区"芯"的特殊性（方案 A/B 分叉，P1/P2 走 A）

- **方案 A（默认）**：芯 = ③ 的 ArkUI 层。自绘档直接垫底没问题；**ReaderKit 档会被引擎
  自己渲染的不透明背景（themeColor）盖住** → RK 档的"芯"实际上由 themeColor 承担
  （皮肤只改框/带/信息条，芯的颜色折算进 themeColor 下发——现有
  `ReaderCustomBg` 管线就是干这个的，按书持久化 + prev 值回退都是现成的）。
- **方案 B（实验开关，后做）**：整页合成图走 `themeBgImg`（SDK
  `@hms.core.readerservice.readerComponent.d.ets:140-159`，`themeBgImg: string`
  「theme background image path.」；`ReaderCustomBg.ets` 头注释已取证两字段并列）。
  优点：皮肤跟页面一起卷、物理感更好。**前置验证**：引擎对透明 PNG 的支持；
  全页图在多机型/横竖屏下的缩放质量。验证通过前不得设为默认（AGENTS.md §3）。

### 5.3 与 NightMode / 主题色的优先级（先定口径，防打架）

```
皮肤素材（有素材的元素） > 主题色 mainColor/secondColor > NightMode 深浅缺省
```

- 有皮肤素材的元素：素材说了算，主题色只染素材声明为"可染色"的部分（SVG fillColor、
  code 颜色里显式引用 mainColor 的占位）。
- 无皮肤素材的元素：维持现状（主题色/深浅档逻辑一行不动）。
- 正文文字颜色永远跟阅读设置（`settingState.fontColor`），皮肤不碰——信息条内容
  现状就是用它（`ReaderPage3.ets:8452` 附近），皮肤只换底板。

## 6. 图标主题（symbol 自定义官方通道，已取证）

1. **官方注册 API**：`symbolRegister.registerSymbol(ttfSrc, jsonSrc): boolean`，
   注册自定义 Symbol 图标资源（TTF）+ 动效参数（JSON）。
   证据：SDK `hms/ets/api/@hms.hds.symbolRegister.d.ts:24-35`（`@since 5.1.1(19)`，
   SystemCapability.UIDesign.Core，支持 phone/tablet/2in1）；官方指南
   `guides/…/UI_Design_Kit（UI设计套件）/应用加载自定义Symbol`（TTF+JSON 放 rawfile，
   Unicode 写进 `string.json`，之后照常 `SymbolGlyph($r('app.string.xxx'))`）。
   本机 SDK API 26 ≥ 19，版本无障碍。
2. **整包注册制**：一个皮肤 = 一套含全部图标的 TTF + 一个动效 JSON，**不是逐图标替换**。
   皮肤包的图标映射（icon key → unicode）写进 manifest。
3. **PNG 禁入图标通道**（染色丢失，§4.2）；SVG 支持染色，作为导入包图标的降级通道。
4. **【待验证】重复调用 registerSymbol 是否整体替换**（换肤热切换的前提）。
   文档未写明。验证方法：真机注册 A 包 → 展示 → 注册 B 包 → 看是否即时生效；
   若不能替换：重启生效，或一次注册多套 unicode 分段（A 包 0x1000xx、B 包 0x2000xx）。
5. **【待验证】registerSymbol 是否接受沙箱文件路径**（用户导入包的前提，§4.4）。
6. 电量 13 态等"同族多态"图标：TTF 里做成连续码位，manifest 按 key 前缀映射
   （`reader.infobar.icon.battery.*` → 0x100030 + 电量档序号）。

## 9. 设计决策记录（为什么这么定 —— 防止未来重新论证）

1. **为什么皮肤层画在引擎之上而不是之下**：ReaderKit 背景是引擎自渲染的不透明
   themeColor，垫底下会被盖住（§5.2）；而带区无正文，画在上面安全且零侵入。
2. **为什么信息条底板是两个 key**：上下两态 padding 公式不同（12/8vp）、贴边方向不同，
   单素材 + 翻转无法覆盖圆角方向；用户明确要"两种素材各自适配"。
3. **为什么图标走 symbol-ttf 而不是图片**：SymbolGlyph 的 fontColor 随主题/深浅天然变色
   （`Index.ets:1864-1866` 的 symbol 化动机），PNG 做不到；SVG 可染色但丢动效参数。
4. **为什么 frame 默认冗余 16vp**：12.2 横屏 RK 横滑偏差 15.1vp + 1vp 余量（§2.6）。
5. **为什么不把皮肤做进 ThemeItem**：ThemeItem 是双色值对象且被 PersistentStorage
   全量序列化，塞资源字段会碰旧数据迁移；皮肤是独立维度，走独立 SkinManager。
6. **否决**：运行时按机型"打补丁"式微调（AGENTS.md §8 一镜到底教训：形态类问题
   一律回到设备级/方向级隔离，不做 if-else 补丁链）。
7. **否决**：用 `ui layout` dump 的运行时节点 bounds 当皮肤定位源——dump 是验收手段，
   不是布局真源；布局真源永远是 §3.2 那组函数（与正文三层同源才能四翻页方式同步）。
