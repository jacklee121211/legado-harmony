# PuraX 外屏「极简阅读」隔离适配

## 0. 一句话方案

**外屏（PuraX 折叠态 1:1 小方屏）自动进入「极简阅读」：启动直奔阅读器，阅读器只留目录 / 书签 / 日夜 / 信息窗；内屏、手机、平板、2in1 一行代码路径都不变。** 全部由「设备形态检测 + 单一布尔」驱动，配一个编译期总闸一键回退。

---

## 1. 关于「外屏申请活动是否结束」的结论（先回应用户的核心担忧）

### 取证到的官方原文

| 依据（`devecocli docs`） | 原文 |
|---|---|
| `FAQ/手机/Pura_X常见问题/Pura_X外屏展示申请前_需要做什么/faqs-purax-2` | 「1. 按照文档完成Pura X外屏适配开发、调测。 2. 适配开发、调测完成后，在应用市场上架成功。」 |
| `…/Pura_X外屏适配申请提交后_多长时间能完成审核/faqs-purax-1` | 「在您提交申请信息后，我们会在5个工作日内回复申请结果，请您留意邮箱消息。」 |
| `…/更多_若以上FAQ仍不能解决_可通过在线提单反馈/faqs-purax-4` | 「问题分类选择"HarmonyOS NEXT->Pura X外屏适配"」 |
| `…/阔折叠布局适配处理方式/faqs-purax-11`（总结） | 「内屏（锁屏或非锁屏状态）切换到外屏，默认显示为锁屏的亮屏状态。用户解锁后，**如果应用已适配外屏**，应用界面将接续到外屏。」 |

**判定：** 本地官方文档里这套「适配 → 上架 → 提交申请 → 5 工作日审核」流程**仍然在，无"已结束"标注**；但线上页面需 JS 渲染，无法取证"活动是否结束"。
⇒ **唯一权威确认渠道 = `faqs-purax-4` 的在线提单**（分类 `HarmonyOS NEXT → Pura X外屏适配`）。建议向官方一次性问三件事：
1. 外屏展示申请入口当前是否仍开放；
2. 若已关闭，**未通过申请的应用在折叠态外屏会显示什么**（锁屏亮屏态？应用界面？黑屏？）；
3. 是否存在随系统版本默认放开的计划。

**为什么这件事不该阻塞开发（三条硬理由）：**
1. **适配是申请的前置条件**（`faqs-purax-2` 第 1 条）。不先适配，将来重开也申请不了。
2. 最坏结果只是**外屏回到系统默认**，内屏/平板/2in1 完全不受影响（本方案是隔离的）。
3. `FoldDisplayMode` 官方注释已写明阔折叠「**内外屏都可作主屏**」——政策方向是放开，不是收紧。

## 2. 形态判定口径（本方案的唯一输入源）

### SDK 依据（`sdk/default/openharmony/ets/api/@ohos.display.d.ts`）

- `:200-209` `isFoldable()`：「For small-screen foldable devices where the outer screen serves only as an auxiliary display (**and cannot be customized by applications**), the return value is always **false**. For other foldable devices, the return value is always **true**.」
- `:801-812` `FoldDisplayMode`：「For foldable devices where **both the inner and outer screens can serve as the primary screen** — like large or **wide-folding models** — the inner screen's display mode is **FOLD_DISPLAY_MODE_FULL**, and the outer screen's display mode is **FOLD_DISPLAY_MODE_MAIN**.」
- `:708+` `FoldStatus`：`FOLD_STATUS_FOLDED = 2`。

### PuraX 屏幕规格（`最佳实践/手机/阔折叠_阔直板应用开发/bpta-purax-guide` 屏幕规格表）

| 形态 | 比例 | vp | px | 断点 |
|---|---|---|---|---|
| PuraX 折叠态（**外屏**） | 1:1 | 326×326 | 980×980 | sm*md |
| PuraX 展开态（内屏） | 16:10 | 440×707 | 1320×2120 | sm*lg |

### 判定函数（新增 `common/utils/OuterScreen.ets`）

```
isOuterMinimal() =
     OUTER_MINIMAL_ENABLED                    // 编译期总闸
  && (调试强制位 forceOuterMinimal === true    // 仅调试/验收用，默认不设
      || ( display.isFoldable() === true
        && display.getFoldStatus() === FOLD_STATUS_FOLDED
        && 窗口高宽比 ∈ [0.85, 1.18]            // PuraX 折叠态 = 1.00；普通手机 ≈2.1，PuraX Max 折叠态 ≈1.46
        && min(窗口宽, 窗口高) ≤ 480vp ))       // 兜住 2in1 正方形窗口等误判
```

**为什么不能只看 `FoldDisplayMode.MAIN`：** Mate X 系列双折叠的**内屏**也是 `MAIN`，会误判。几何比例才是唯一可判据 —— 且它天然把 PuraX Max 折叠态（14:10 = 1.46）排除在外，符合用户「只要 PuraX 那个正方形屏」的口径。

**实时维护：** 在 `EntryAbility.onWindowStageCreate` 的 `getMainWindow` 回调里，紧跟现有断点注册（`EntryAbility.ets` 的 `updateBreakpoint` + `windowClass.on('windowSizeChange')` 那一段）追加：
- 启动时算一次；
- `windowSizeChange` 时重算（折叠/展开必然改变窗口尺寸）；
- `display.on('foldStatusChange')` 时重算（折叠态先变、尺寸后到，双保险）；
- 结果写 `AppStorage('outerMinimal')`，业务侧一律 `@StorageProp` / `@StorageLink` 订阅，**不散落判断**（对齐 AGENTS.md §7「两态并存判断造成排查混乱」的教训）。

**为什么用 `FoldStatus` 而不是 `FoldDisplayMode` 做实时事件：** SDK 明确 `foldStatusChange` 与 `foldDisplayModeChange` 是两个事件且「折叠状态先变，底层再据此匹配显示模式」。两者都监听，以几何为准。

## 3. 目标行为

### 内屏 / 手机 / 平板 / 2in1 —— **零变化**
`outerMinimal === false` 时，所有新增分支全部不进入，等价于改动前的代码路径。

### PuraX 外屏 —— 极简阅读

**A. 启动**
- 冷启动检测到外屏 ⇒ **直奔阅读器**，读「最后阅读的那本书」。
  复用现有链路，不新写：`BooksDao.getLastReadBook()` → `AppRouter.push(RouteName.READER, rp)`（即 `Index.openLastReadBook(false)`）。
- **无阅读记录时** ⇒ 显示极简卡片（见 B），**绝不**在 326×326 上渲染完整书架。

**B. 外屏的「首页」= 极简「继续阅读」卡片**（新组件 `OuterHomeCard.ets`）
- 内容：封面 + 书名 + 「继续阅读」按钮 + 一行灰字「展开手机使用完整功能」。
- 它同时是**阅读器的返回落点**。
- 在 `Index.build()` 里：`if (this.outerMinimal) { OuterHomeCard() } else { <现有 HdsTabs 四页签整块> }`。
  ⚠️ 现有 `HdsTabs` 整块保持原样不动，只外包一层条件 —— 这是「不破坏现有功能」的关键。

**C. 阅读器精简版**（`ReaderPage3.ets` 就地加门，不复制文件）

| 用户要求 | 落地方式 |
|---|---|
| ❌ 听书模块 | ① dock 不渲染听书格 ② `openListenDialog()` 首行 return ③ `TtsMiniBar()`（`ttsState !== 'stopped'` 那处）不渲染 ④ `ImmersiveListenLayer()` 不渲染 |
| ❌ 上一章/下一章/进度条 | 整个「进度胶囊」`Column({ space: 20 }) { Row{上一章 Slider 下一章} }` 不渲染 |
| ❌ 顶部栏 | 顶栏 `Column(){ 返回 + 章节名 + 旋转 + 防窥 + 书签 }` 整块不渲染 |
| ❌ 设置模块 | ① dock 不渲染设置格 ② `openSettingDialog()` 首行 return ③ `settingDialog` 不 open |
| ❌ 系统状态栏 | 进场时强制 `readerStatusBarOn = false`（**压过**设置页开关，符合「就算这个开关开着，对于外屏也无效」） |
| ✅ 目录 | dock 第 1 格 + `openCatalogDialog()` 原样 |
| ✅ 书签 | dock 第 2 格 + `openBookmarkDialog()` 原样 |
| ✅ 日间/夜间/自由 | dock 第 3 格 + `dispatchBarAction(3)` 原样 |
| ✅ 信息窗（顶部） | `if (!this.isShowSetting && this.infoWinOn)` 原样保留（顶栏消失后它天然常显） |
| ✅ 底部 3 个 dock 图标 | dock 由 5 格变 3 格 |

**D. 退出路径**：顶栏取消后无返回按钮 ⇒ 依赖**系统侧滑/返回键** → 回落到极简卡片（B）→ 再返回退出应用。

## 4. dock 从 5 格变 3 格（唯一有真实回归风险的地方）

现状（`ReaderPage3.ets`）：`Tabs` 内 5 个 `TabContent`，各自 `.tabBar(this.ReaderBarItem(action, pos))`，
**action 与 pos 是两套编号**（注释明写"语义不同，别合并"）：
`action: 0=目录 1=书签 2=听书 3=日夜 4=设置`，正常态 `pos === action`。

**改法（最小、零下标重算）：**
```
// outerMinimal === false（原样 5 格）
ReaderBarItem(0,0) ReaderBarItem(1,1) ReaderBarItem(2,2) ReaderBarItem(3,3) ReaderBarItem(4,4)
// outerMinimal === true（3 格，action 保持原 id ⇒ dispatchBarAction 与 readerBarLabel 一行都不用改）
ReaderBarItem(0,0) ReaderBarItem(1,1) ReaderBarItem(3,2)
```
- `barScale: number[] = [1,1,1,1,1]` 长度不变（只用 pos 0..2）。
- `dispatchBarAction(index)` / `readerBarLabel(action)` **完全不动**。
- ⚠️ 仍然**不给 `Tabs` 挂 `.onTabBarClick()`**（工程已实测：它会派发多次且首个 index 恒 0）。

## 5. 一镜到底：修好它，而不是关掉它（回应用户「PuraX Max / X 系列 / XT 系列都完了」）

### 问题机制（工程内已记录，AGENTS.md §7）

`CardLongTakeDelegate.build()` 把阅读页包进一个写死尺寸的裁切盒：
```
Stack{ Stack{ ReaderPage3 }.width(winWvp).height(winHvp).scale(bookScale) }
  .width(bookW).height(bookH).clip(true)
```
`winWvp/winHvp` 在 `LongTakeSession.initGeometry()` 里**只算一次**（`LongTakeSession.ets:175-176`）；
`setNewSize()` 只写 `navDestSize`（`:507-509`）⇒ **盒子永不跟随窗口**。
折叠 = 窗口尺寸剧变（440×707 → 326×326vp）⇒ 阅读页按旧尺寸排版被裁 ⇒ 挤压/空白。

### 关键取证：修复成本很低

`WindowUtils.init()` 已经注册了 `windowSizeChange`，并**实时更新** `windowWidth_px/windowHeight_px`（`WindowUtils.ets:41-47`），还广播了 `ON_WINDOW_SIZE_CHANGED`。
且 `LongTakeSession` 是 `@Observed`（`:63`）、delegate 用 `@ObjectLink` 接（`CardLongTakeDelegate.ets:31`）⇒ **改字段就能驱动重绘**。
两个文件都在**工程内**（`entry/src/main/ets/common/ezlt/`），不是 oh_modules ⇒ 可改。

### 改法

在 `LongTakeSession` 新增：
```ts
/**
 * 窗口尺寸变化后重新对齐书盒（折叠 / 旋转 / 2in1 拖窗口）。
 * 只在"已落定阅读态"生效；转场进行中一律跳过（否则会把飞行轨迹改歪）。
 */
public syncBoxToWindow(): void {
  if (!UiMotion.LT_BOX_FOLLOW_WINDOW) { return; }          // 一键回退
  if (this.bookScale < 0.999 || this.radiusProgress > 0.001) { return; }  // 转场中
  const wPx = WindowUtils.windowWidth_px, hPx = WindowUtils.windowHeight_px;
  if (!wPx || !hPx || this.cardItemInfo_px.width <= 0) { return; }
  const wVp = px2vp(wPx), hVp = px2vp(hPx);
  if (Math.abs(wVp - this.winWvp) < 0.5 && Math.abs(hVp - this.winHvp) < 0.5) { return; }
  this.winWvp = wVp;
  this.winHvp = hVp;
  this.s0 = this.cardItemInfo_px.width / wPx;   // 返回动画起点比例同步
  this.applyReadingFull();                       // bookW/H → 新窗、bookScale = 1
  this.logProbe('window-sync');
}
```
调用点：`LongTakeSession.setNewSize()` 末尾调一次（`Index.ets` 两个 `NavDestination.onSizeChange` 已经在调 `setNewSize`，**无需改 Index**）。

### 收益与代价
- ✅ **所有折叠机型（PuraX / PuraX Max / Mate X / XT）都保留一镜到底** —— 直接满足用户要求。
- ✅ 顺带修掉工程里既有的「折叠/旋转后阅读页被毒化」隐患（平板旋转那条老 bug 的同一根因）。
- ⚠️ 新增一个行为：转场落定后窗口变化会重排书盒 —— 必须真机验证"折叠瞬间"无闪烁。
- **回退**：`UiMotion.LT_BOX_FOLLOW_WINDOW = false`（新增常量，默认 `true`）⇒ 恢复"盒子固定"的旧行为。

### 兜底（若真机验证失败）
一级回退：`LT_BOX_FOLLOW_WINDOW = false`，同时在 `isLongTakeEnabledDevice()` 里追加
`&& AppStorage.get<boolean>('outerMinimal') !== true`（**只在外屏态禁用**，不影响任何折叠机型的内屏）。
**不做**「所有折叠设备一律禁用」（用户已明确否决）。

## 7. 关键风险与对策

| # | 风险 | 对策 |
|---|---|---|
| R1 | 一镜到底盒子不跟随窗口 ⇒ 外屏阅读页挤压/空白 | 第 5 节 `syncBoxToWindow()`；兜底 `LT_BOX_FOLLOW_WINDOW=false` + 仅外屏态禁用 |
